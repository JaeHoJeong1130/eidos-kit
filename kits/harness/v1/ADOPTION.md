# 설치 후 프로젝트에 맞게 정리하기

**키트 설치는 공통 작업 구조를 갖추는 단계입니다. 기존 프로젝트의 규칙과 작업 방식까지 자동으로 최적화하지는 않습니다.**
GitLab과 GitHub 중 어디에서 키트를 받았든 같은 후속 정리가 필요합니다.
`doctor` 성공은 설치 상태와 계약 검사의 통과를 뜻합니다. 기존 규칙 사이의 중복·충돌,
검증 비용, 실제 업무 흐름의 적합성까지 모두 확인했다는 뜻은 아닙니다.

**기존 상태 확인 → 공식 도구로 적용 → 프로젝트에 맞게 정리 → 실제 Work로 확인** 순서로 진행하세요.
신규 프로젝트도 실제 목표·담당자·검증 방법을 설정해야 합니다. 기존 프로젝트에는 기존 규칙과의 대조가 추가됩니다.

이 안내의 Direction·Eidos owner·Work·claim 절차는 Eidos를 사용하는 프로젝트에 적용합니다.
Harness를 `--without-eidos`로 설치했다면 Eidos 설정과 명령은 생략하고, 프로젝트의 기존 목표·담당자·실행 기록으로
실제로 필요한 작은 작업 하나의 시작·검증·종료를 확인하세요. 후속 정리를 위해 Eidos 설치를 추가로 요구하지 않습니다.

## 적용 전에 보존할 것

대상 Git 저장소의 루트, 현재 커밋, 수정 중인 파일을 먼저 확인하고 변경 전 상태와 복구 근거를 남깁니다.
기존 AGENTS, 도메인 규칙, 작업 절차, 테스트, Failure, Direction, Work, 참여자 목록과 폴더 역할을 확인하세요.
설치 충돌을 없애려고 기존 규칙이나 작업 이력을 삭제하지 않습니다.

다음 명령은 받은 키트 폴더에서 실행합니다. 경로는 실제 대상 프로젝트로 바꿉니다.

```powershell
py -3.13 -B kits/harness/v1/harness_kit.py assess --root C:\project\existing-project
```

관리 대상 경로가 없는 프로젝트는 `install`, 기존 비관리 구조가 있는 프로젝트는 상태에 맞는 사전 정리 후
`migrate`, 이미 관리되는 설치본은 `diff`·`upgrade`·`doctor` 절차를 사용합니다.
`migrate`도 모든 기존 문서를 자동으로 재작성하는 명령은 아닙니다. 보존할 프로젝트 소유 파일이
현재 계약을 충족해야 하며, 충돌 파일에는 별도 조건이 있습니다.
명령과 선행 조건은 [Harness 설치 안내](README.md)를 확인하세요.
Eidos만 사용하는 경우에는 [Eidos 단독 설치 안내](../../eidos/v3/README.md)를 따릅니다.

## 적용 후 확인할 여섯 가지

| 확인 대상 | 프로젝트에 맞게 정리할 내용 |
| --- | --- |
| 진입점과 규칙 | 하나의 위험도 경로에서 필요한 도메인 규칙을 찾을 수 있게 연결합니다. 기존 기준은 보존하고, 중복 문서의 정본과 참조 관계를 명확히 합니다. |
| Direction | 예제 문구를 실제 목적·범위·Stage·완료 조건으로 바꿉니다. 이미 확정한 방향과 과거 기록을 보존합니다. |
| 담당자 | 확인된 실제 사람을 활성 `member:*`로 등록하고 이번 Work의 owner를 선택합니다. 기존 참여자·aliases·과거 Work는 보존합니다. |
| Work와 지식 | 실행 결과는 Work, 재사용할 예방 규칙은 Failure에 남깁니다. 프로젝트에서 Memory를 쓴다면 안정된 지식의 위치를 안내하고, 실패 기록 위치가 문서마다 다르지 않게 합니다. |
| 검증 범위 | 문서·국소 구현·공유 동작·외부 계약 변경을 실제 영향으로 구분하고, 각 범위에 필요한 검사와 소비자를 연결합니다. 기존 필수 기준을 누락하지 않습니다. |
| 폴더와 기존 도구 | 기존 경로를 사용하는 코드·스크립트·정책을 확인합니다. 폴더를 일괄 이동하기보다 역할과 링크부터 정리하고, 사용하는 경우 `_meta/layout.json`에 실제 배치를 반영합니다. |

Git 작성자나 GitLab·GitHub 로그인에서 Eidos owner를 추정하지 않습니다. 배포자의 이름이나 예제 ID도 기본값이 아닙니다.
담당자 확인 전에는 가상의 owner로 Work를 만들지 말고, 초기 설정의 근거를 프로젝트의 기존 기록 방식으로 남기세요.

## 검증 범위를 줄일 때 지킬 조건

검증 최적화는 변경 영향에 맞게 검사를 선택하는 일입니다. 실패한 검사를 제외하거나 기존 안전 기준을 약화하는 수단이 아닙니다.

1. 기존 필수 검사가 보호하는 동작과 영향을 받는 소비자를 먼저 대응시킵니다.
2. 변경 예정 경로로 적용 규칙을 선택하고, 실제 변경 경로가 확정되면 다시 확인합니다.
3. 선택한 검사와 제외한 검사의 이유를 Work에 남깁니다. 기존 필수 범위를 바꾸려면 해당 프로젝트의 변경·검토 절차를 따릅니다.
4. 운영 정책을 바꾸는 문서는 도메인 검사도 적용합니다. 공유 동작은 모든 관련 소비자를 확인하고, 영향이 불명확하면 범위를 넓힙니다.
5. 프로젝트가 요구하는 독립 검토와 승인 경계를 유지합니다. 키트 구조 검사로 제품 테스트를 대체하지 않습니다.

특정 프로젝트의 Pester, 스캐너, 전체 테스트 조합을 모든 수신자에게 공통 적용하지 않습니다.
각 프로젝트의 언어·도구·실행 부작용에 맞게 정하고, 검증 시간을 비교할 때는 검사 범위도 함께 기록하세요.

## 공통 키트와 프로젝트 설정의 경계

프로젝트에 맞춘 절차는 소유권 매니페스트가 프로젝트 소유로 선언한 파일이나 별도 프로젝트 문서에 둡니다.
키트 소유 파일을 직접 고치거나, 검사 통과를 위해 해시·검증기를 수정하지 않습니다.
공통 계약을 개선할 필요가 있다면 키트 소스에서 별도 변경·검증·릴리스 절차를 거칩니다.

업그레이드는 프로젝트 소유 설정을 보존합니다. 따라서 기존 로컬 지침의 중복이나 낡은 검증 범위도
자동으로 정리되지 않을 수 있습니다. 적용 후 대조와 실제 사용 중의 후속 정리가 계속 필요합니다.
이 안내 자체가 파일 삭제·일괄 이동·원격 push를 승인하지는 않습니다.

Harness 1.9.0의 조회 경량 경로는 새 프로젝트의 bootstrap에 포함됩니다. 기존 AGENTS가 모든
요청에서 context·routing·contract 읽기를 요구하면 upgrade 후에도 그 프로젝트 규칙이 적용됩니다.
채택 시 순수 조회의 진입 조건과 편집 전 필수 절차를 함께 정리하고, 운영 기록 등 필수 스킬의 호출
누락도 확인하세요. 새 세션에서 설치본과 노출된 스킬 설명을 확인해야 실제 적용 여부를 판단할 수 있습니다.

## 실제 Work 하나로 준비 상태 확인하기

설치한 대상 프로젝트에서 구조와 현재 상태를 확인합니다.

```powershell
py -3.13 -B .agents/tools/harness.py validate --root .
py -3.13 -B .agents/tools/eidos.py validate --root .
py -3.13 -B .agents/tools/eidos.py focus --root . --summary --json
```

Harness 없는 Eidos 단독 설치에서는 Harness 명령을 생략하고 프로젝트의 검증 절차를 사용합니다.
Eidos 없는 Harness 단독 설치에서는 Eidos `validate`·`focus`와 아래 Work·claim 절차를 생략하고 기존 작업 절차를 확인합니다.
Work를 시작하려면 저장소에 초기 커밋이 있어야 합니다. 아직 없다면 프로젝트의 커밋 절차에 따라 준비합니다.
확인된 owner로 작지만 실제로 필요한 작업 하나를 선택하고, 계획과 범위를 기록한 뒤
실행·검증·필요한 검토·정상 종료와 claim 해제까지 확인합니다.
명령과 입력 형식은 [Work 절차](../../eidos/v3/template/.agents/workflows/eidos-v3.md)를 참고하세요.
설정 전에 끝난 작업을 새 Work에서 수행한 것처럼 소급 기록하거나, 예제 성공 결과를 복사하지 않습니다.

실제 Work 한 번의 성공은 해당 범위의 운영 절차를 확인한 근거입니다. 모든 제품 기능이나 Direction의
완료 조건을 통과했다는 뜻은 아닙니다. 결과에는 다음을 구분해서 남깁니다.

- 설치 상태: 버전, 구조 검사, 남은 경고.
- 운영 준비: 실제 목표·담당자·규칙 연결·검증 절차와 완료한 Work의 근거.
- 남은 항목: 미설정 사항, 이번에 검증하지 않은 범위, 다음 실제 작업에서 조정할 부분.

## 에이전트에게 요청할 문장

아래 값은 실제 경로와 확인된 사람의 ID로 바꾸세요.

```text
받은 키트는 <키트 폴더>, 적용할 기존 프로젝트는 <프로젝트 폴더>야.
나는 <이름>이고 이번 Work의 Eidos owner는 <확인된 member:ID>야.
기존 규칙과 수정 중인 파일을 보존하면서 공식 도구로 적용하고,
설치 완료와 운영 준비 완료를 나누어 보고해줘.
설치 후 프로젝트 소유 지침에서 진입점·중복 규칙·실패 기록 위치를 정리하고,
실제 목표와 담당자, 변경 영향별 검증 범위를 맞춰줘.
검사를 줄이기 전에 기존 필수 기준과 영향받는 동작을 확인하고,
안전·승인 경계와 필요한 독립 검토는 유지해줘.
작지만 실제로 필요한 Work 하나를 시작·검증·종료해 절차를 확인하고,
남은 미설정 항목과 추가 최적화 사항을 구분해서 알려줘.
```
